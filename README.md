# 获客助手 网页版

在自己的浏览器里采小红书和抖音的帖子和评论，挑出想找对象的人，把私信和评论发出去。Mac 和 iPhone 都能用，不用装 app，不用 Xcode，不用开发者账号。

安装和使用说明在 <https://goose666666.github.io/xhs-collect-web/>。

## 这是什么

一个用户脚本加一个静态网站。

用户脚本挂在小红书页面上，在页面右下角加一个面板。面板负责选词、跑采集、看数据、出话术。采到的东西存在浏览器的 IndexedDB 里，不上传任何地方。

静态网站做三件事：给出安装步骤；提供一个控制台，打开它就能登录、采集、发私信；提供一个看板，把导出的 json 文件在电脑上打开来看。

控制台自己什么都干不了，浏览器不允许一个域的网页去读另一个域的登录态和数据。它做的是另一件事：开一个小红书的标签页，那边装着用户脚本，真正的活全在那边干，两边用 postMessage 说话。结构跟手机版 app 里控制台加 WebView 是一样的，只是中间那层从进程内调用换成了跨标签页的消息。

手机上别用控制台。Safari 一切走标签页就把后台那页挂起，采集跟着停，所以手机上直接用小红书页面里那个面板，两者是同一套东西。

## 为什么不是一个普通网页

托管在 GitHub Pages 上的网页登不了小红书也采不了数据。浏览器的同源策略挡着，页面既读不到小红书的 cookie，也钩不到它页面里的 fetch。

所以采集这部分必须跑在小红书自己的页面上，这正是用户脚本能做而普通网页做不到的事。登录也因此不需要单独做：用户在 Safari 里正常登录小红书，脚本用的就是那个会话。

## 原理

跟安卓版是同一套。安卓版在自己的 WebView 里注入脚本钩住 fetch 和 XHR，网页版把同一段脚本注入到小红书页面里，钩的是同一批接口，解析用的是同一套字段规则。

小红书的接口带签名，自己拼请求几乎不可能。但只要让页面自己去请求，返回就是完整的，跟人工浏览没有区别，我们只是把返回的 JSON 抄一份。

## 跟安卓版最大的不同

安卓版整轮采集跑在一个不会消失的对象里。网页版每打开一篇帖子就是一次真正的页面跳转，脚本会被整个重新加载，内存里的东西全没。

所以 `70-engine.js` 写成一台状态机：每走一步就把进度写回库，新页面起来之后读回进度，看自己该干什么，接着干。中途关掉标签页、手机锁屏、甚至重启浏览器，回到小红书都能接着跑。

## 构建和测试

```
node build.js
node test/run.js
```

构建只做拼接，不打包不压缩。这个脚本要装在别人的浏览器里，跑在他自己的账号上，看不懂的代码不该让人装。

测试里的断言是从安卓版 `test/` 下的 Dart 测试搬过来的，值一模一样。两端的解析和话术必须给出同样的结果，不然手机采的和网页采的数据摞不到一起。

## 跟另外两端的关系

三端的表结构和字段名完全一致：

- 电脑版 Python 加 Playwright，在 `手机软件/小红书获客智能体`
- 安卓版 Flutter，在 `D:\software\xhs-app`
- 网页版就是这个仓库

导出的 json 和 csv 可以在三端之间互相导入。

## 限速是硬约束

默认三十分钟采五十篇，一批私信二十个二十分钟发完。平台识别批量行为看的是节奏，不是浏览器指纹。密集访问轻则接口返回空数据、弹滑动验证，重则封号。慢一点最多是多花几小时，号没了是全部归零。

发送的间隔是开跑前一次随机切好的，长短参差不齐，加起来正好是设定的总时长。每次现算一个随机数的话，所有间隔都挤在平均值附近，那个规律性本身就是特征。

## 小红书的私信键点不动

手机版是让程序对着屏幕真按一下绕过去的，那是系统级的触摸事件。用户脚本没有这个本事：小红书主页上那个私信键只认真实手势，JS 调 click 也好，派一整套鼠标和指针事件也好，页面一点反应都没有。

所以网页版到这一步会停下来，把那个键标红请人按一下，按完程序接着把话填进去、发出去、核对。抖音的私信键脚本点得动，全程不用管。

公开评论的最后一下一律由人按，这一条跟手机版一致，不是网页版的限制。评论是贴在别人门面上的，最招举报。人按下去的那一刻程序看不见，所以这条路不查结果、不记流水、也不占额度，记了就是拿猜的结果冒充事实。
